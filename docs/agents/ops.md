# Ops: auth, admin, alerts, health, speed

Sign-in, admin, alerts, health checks, pgsites calls and request timing. Moved verbatim from the root `CLAUDE.md`. Paths are from the repository root.

- **Auth:** Better Auth with GitHub and Google OAuth (`app/lib/auth.server.ts`). Better Auth is imported on first use (`createAuth` returns a promise), so a visitor with no session cookie never loads it. `getSession` looks the session up once per request, keyed by the env object `worker.ts` makes for each request, so call it freely from any loader. The header reads the user from the root loader, never `authClient.useSession()`. Sign-in is `/login` (old `/auth/signin` links redirect). `trustedOrigins` is the site's own origin.
- **Admin:** `user.role` is `'user'` or `'admin'` (`src/lib/admin.ts`). It is a Better Auth additional field with `input: false`; keep it that way, or Better Auth's own `POST /api/auth/update-user` would let any pilot make themselves an admin. `/admin` (`app/routes/admin.tsx`, `admin._index.tsx`, `admin.users.tsx`, data in `app/lib/admin.server.ts`) has the health report, the live build, pilot counts and page speed, and every pilot with a button to change their role. Every loader and action under `/admin` calls `requireAdmin` itself, since React Router can run one route's loader or action without its layout's. Make the first admin with `npm run make-admin -- <email>` (`--prod` for production, `--list` to list them) or the "Make admin" workflow; the script and workflow come from pjmgmt's admin-section standard (`scripts/automations/templates` in mckinley/pjmgmt), so change them there. The repo is public: never print a pilot's email in a log or workflow (the workflow masks them). The live build shows the commit (`__COMMIT_SHA__`, set in `vite.config.ts` from `GITHUB_SHA`) and the Worker version (the `CF_VERSION_METADATA` binding).
- **Alerts:** an hourly Cron Trigger (`[triggers]` in `wrangler.toml`) runs `worker.ts` `scheduled`, which posts to `/api/notifications/check`. Each user's morning run (digest) is at their digest hour and the evening run at 18:00, in their `settings.timeZone` (`src/lib/alert-schedule.ts`). `?run=morning|evening` with the `CRON_SECRET` bearer forces a run for everyone.
- **Health:** the checks are `runHealthChecks` in `app/lib/health.server.ts`: D1 write, Open-Meteo forecast, pgsites search and daily sync age (with what Paragliding Earth answered when pgsites' daily sync failed), last alerts run, season build and NOGA copy. After the alerts run, the cron calls `/api/admin/health` (CRON_SECRET bearer, or a signed-in admin), which runs them, and stores the report in `app_state` (`health_last_report`). The public `/api/health` answers from that report (check names and results only, `publicHealth` in `src/lib/health.ts`): 200 when it passed within two hours, else 503, for uptime monitors such as pjmgmt's. It emails the `HEALTH_ALERT_TO` secret when the set of failing checks changes (`healthState` in `src/lib/health.ts`, so a new problem emails while an old one still fails) and throws, so the cron shows as failed in Cloudflare. State is in the `app_state` table.
- **pgsites calls** go through `fetchApi` in `src/lib/pgsites-client.ts`, which reuses answers from the Worker's edge cache for `PGSITES_CACHE_SECONDS` (6 h; a pgsites call can take a second when its Worker starts fresh). Pass `{ fresh: true }` where a live answer matters (the health check, `getSyncStatus`).
- **Speed:** every response carries a `Server-Timing` header (total, `cold` for a fresh Worker start, D1 queries, calls to Open-Meteo, pgsites and other hosts), and each page or `.data` load keeps a row in `request_timings` (page pattern such as `/sites/:slug`, never which site; newest 2000). `src/lib/request-timing.ts`, wired in `worker.ts`. The "Perf probe" workflow prints them with the D1 region and Open-Meteo timing.
